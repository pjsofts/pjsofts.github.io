خواندن سورس ابزارهای AI که واقعاً شیپ شده‌اند، سریع‌ترین راه یادگیری معماری ایجنت است. دو تا از آموزنده‌ترین‌ها **Grok Build** (ایجنت کدنویسی Rust از xAI) و **Claude Code** (نسخهٔ تایپ‌اسکریپتی Anthropic) هستند. هر دو همان کار را انجام می‌دهند — کدتان را می‌خوانند، فایل‌ها را ویرایش می‌کنند، دستور اجرا می‌کنند، وب را جست‌وجو می‌کنند، کارهای طولانی را مدیریت می‌کنند — اما توسط تیم‌هایی ساخته شده‌اند که تقریباً **شرط‌بندی‌های مهندسی متضادی** انجام داده‌اند.

هیچ‌کدام «درست» نیست. TypeScript شما را در یک آخر هفته به یک ایجنت کارا می‌رساند. Rust در ازای کد بسیار بیشتر، سندباکس در سطح سیستم‌عامل، موازی‌سازی واقعی و یک باینری واحدِ قابل‌شیپ می‌خرد. هدف از خواندن هر دو این است که ببینید کدام تصمیم‌ها *ضروری‌اند* و کدام‌ها *سلیقه*.

## دو ایجنت، یک کار، غریزه‌های متضاد

بزرگ‌ترین دوراهی، همان اولین دوراهی است: **زبان**.

- **Claude Code** تایپ‌اسکریپت روی Node/Bun است — یک پروسه، یک ران‌تایم async، و یک UI از جنس React-در-ترمینال.
- **Grok Build** با Rust است — یک ورک‌اسپیس با بیش از 70 کریت (crate)، ران‌تایم async از نوع `tokio`، و یک اپ ترمینالی تمام‌صفحه.

همه‌چیزِ پایین‌دستی — نحوهٔ سندباکس، نحوهٔ ماندگارسازی سشن‌ها، نحوهٔ رندر — از همین تصمیم سرچشمه می‌گیرد. این هم نقشه، پیش از آنکه قدم‌به‌قدم برویم:

| بُعد | Grok Build | Claude Code |
|---|---|---|
| زبان | Rust (بیش از 70 کریت، یک باینری) | TypeScript (Node/Bun) |
| مدل async | تسک‌ها و کانال‌های `tokio` | جنراتورهای async (`async function*`) |
| UI ترمینال | تمام‌صفحه با `ratatui` (alt-screen) | این‌لاین با Ink/React (اسکرول‌بک) |
| سندباکس | Landlock + Seatbelt + seccomp + bwrap | seccomp (لینوکس) + Seatbelt (مک) |
| شمارش توکن | هیوریستیک `bytes/4` | مبتنی بر توکنایزر + هیوریستیک |
| سشن‌ها | ایندکس‌های SQLite + چک‌پوینت‌های JSON | ترنسکریپت‌های JSONL فقط-افزودنی |
| تعبیه در ادیتور | ACP (Agent Client Protocol) | افزونه‌های IDE / SDK |
| فایل حافظه | `AGENTS.md` / `.grok/rules` | `CLAUDE.md` + دایرکتوری حافظه |

## یک باینری در برابر یک پروسه

هر دو ریپو را باز کنید و تفاوت بلافاصله به چشم می‌آید. Claude Code درختی از ماژول‌های TypeScript زیر `src/` است — `query.ts`، `Tool.ts`، `tools/` — که با یک موتور JS کامپایل و اجرا می‌شود. Grok Build یک **ورک‌اسپیس** Cargo است: ده‌ها کریت کوچک که هر کدام مرزی سخت است که کامپایلر آن را تحمیل می‌کند.

Grok بیش از 70 کریت خود را به `crates/common` (قابل‌استفادهٔ مجدد: tool-runtime، فشرده‌سازی، circuit-breaker) و `crates/codegen` (خودِ ایجنت: ابزارها، شل، سندباکس، TUI) تقسیم می‌کند. کریتی مثل `xai-tool-runtime` عملاً نمی‌تواند به UI وابسته باشد — این مرز در کامپایل تعبیه شده است. حتی SDK مربوط به MCP در کریت خودش قرنطینه شده تا نسخه‌های وابستگی‌هایش نشت نکند.

Claude Code همان مرزها را **با قرارداد** ترسیم می‌کند: `query.ts` حلقه است، `Tool.ts` قرارداد ابزار، و `tools/` پیاده‌سازی‌ها. هیچ چیزی مانع نمی‌شود که یک فایل UI یک فایل هسته را ایمپورت کند؛ نظم بر عهدهٔ نویسنده است، نه کامپایلر.

این بده‌بستان واقعی است. مرزهای زمانِ کامپایل با مشارکت‌کنندگان زیاد مقیاس‌پذیرند — تغییری در کریت شل نمی‌تواند تصادفاً درونیات کریت سندباکس را بشکند. برای یک پروژهٔ تک‌نفره این سربار به‌صرفه نیست، و دقیقاً به همین دلیل است که آموزش از یک پکیج واحد شروع می‌شود. درسی که در هر صورت باید نگه دارید: **ایجنت شما باز هم باید درز (seam) داشته باشد**. آیا می‌توانید UI ترمینال را با یک UI وب عوض کنید بدون آنکه به حلقهٔ ایجنت دست بزنید؟ Grok می‌تواند (از طریق ACP)؛ شما هم همین را هدف بگیرید.

## حلقه‌ای در مرکز همه‌چیز

این قلب هر ایجنتی است، و نکتهٔ چشمگیرِ خواندن هر دو این است که **دقیقاً همان کار را می‌کنند**. قاعده چنین است: *مدل را فراخوانی کن؛ اگر ابزار خواست، اجرایشان کن و دوباره حلقه بزن؛ اگر نخواست، کار تمام است.*

این هم جوهرهٔ ماجرا، در همان حدود 40 خطی که خودتان می‌نوشتید:

```python
for _ in range(MAX_STEPS):
    msg = call_model(messages, tools)
    messages.append(msg)
    if not msg.tool_calls:
        return msg.content            # model gave a final answer -> STOP
    for call in msg.tool_calls:       # else run every requested tool
        result = TOOL_FNS[call.name](call.args)
        messages.append(tool_result(call.id, result))
    # loop again with the results appended
```

و این هم شرط توقف واقعی Grok، در Rust — زبانی دیگر، منطقی یکسان:

```rust
let tool_calls = response.tool_calls().to_vec();
if tool_calls.is_empty() {
    // (maybe nudge about pending TODOs / drain interjections, else:)
    return Ok(TurnOutcome::Completed { .. });   // STOP
}
execute_tool_calls(tool_calls).await?;          // run them...
// ...fall through and loop again
```

قاعدهٔ حلقه پیش‌پاافتاده است. **مقاوم و پاسخگو** کردنش نه. جنراتور async در Claude Code کد را خطی و آسان‌فهم نگه می‌دارد. طراحی Grok نوبت را بین اکتورهایی که روی کانال‌های `tokio` با هم حرف می‌زنند تقسیم می‌کند — یک اکتور سشن مالک حلقهٔ نوبت است، یک اکتور sampler مالک فراخوانی‌های مدل، یک اکتور chat-state مالک تاریخچه — که در ازای ماشین‌آلات بسیار بیشتر، همروندی می‌خرد (استریم پاسخ در حالی که UI زنده می‌ماند، لغو فوری یک درخواست در جریان، اجرای موازی ابزارها). همان مغز، سیستم عصبی متفاوت.

### پروداکشن دور حلقه چه می‌پیچد

این‌ها لایه‌هایی هستند بین یک حلقهٔ هفته-چهارمی و یک ایجنت شیپ‌شده — ارزش نام‌بردن دارند تا بدانید «تمام» در نهایت یعنی چه:

| دغدغه | Grok Build | در کلون شما |
|---|---|---|
| سقف حلقه | ادامهٔ مبتنی بر policy | یک `MAX_STEPS` ثابت |
| API ارائه‌دهنده | یک استریم ایونت روی 3 بک‌اند | یک فراخوانی SDK |
| تلاش مجدد | backoff نمایی، حداکثر 15 بار، سقف 30 ثانیه + jitter | بعداً اضافه کنید |
| استریم مسموم | بودجهٔ جداگانهٔ resample برای «doom-loop» | — |
| لغو | `CancellationToken` برای هر درخواست، cancel-on-drop | Ctrl-C |
| ابزارهای موازی | fan-out با dispatch همروند | یک حلقهٔ `for` |

دو جزئیات ارزش نگاه دقیق‌تر دارند. اول، Grok **سه** API متفاوتِ ارائه‌دهنده — OpenAI Chat Completions، OpenAI Responses و Anthropic Messages — را به یک استریم یکنواخت `SamplingEvent` نرمال می‌کند (`StreamStarted`، `ToolCallDelta`، `Completed`…)، طوری که باقی ایجنت هرگز نمی‌داند با کدام مدل حرف می‌زند. این پاداشِ گذاشتن یک **درز** میان *«تصمیم دربارهٔ گام بعدی»* و *«حرف زدن به گویش این ارائه‌دهنده»* است. (یک نکتهٔ ظریف که خیلی‌ها را می‌لغزاند: «Chat Completions» نام یک *فرمت سیمی* است، نه یک سرویس — هر هاستی در کد Grok متعلق به xAI است. سازگار با OpenAI ≠ خود OpenAI.)

دوم، تصمیم Grok برای ادامهٔ حلقه غنی‌تر از «آیا تول‌کالی هست؟» است. وقتی پنجره پر شده، فشرده‌سازی می‌کند و دوباره می‌فرستد؛ احراز هویت را تازه می‌کند؛ پیامی را که وسط نوبت تایپ کرده‌اید تخلیه می‌کند؛ یا یک **todo-gate nudge** شلیک می‌کند که نمی‌گذارد مدل در حالی که TODOها ناتمام‌اند نوبت را تمام کند. هر کدام یک policy کوچک است که به همان حلقه پیچ شده — الگویی خوب برای اینکه حلقهٔ خودتان را چطور رشد بدهید.

## قرارداد ابزار

هر دو ایجنت به یک ایدهٔ مرکزی همگرا می‌شوند: ابزار یعنی یک تابع به‌علاوهٔ یک اسکیمای ماشین‌خوان، که با نام dispatch می‌شود. اما شکل قرارداد به‌شدت متفاوت است.

Grok یک `trait Tool` در Rust با associated typeهای *تایپ‌دار* تعریف می‌کند (`Args: Deserialize`، `Output`) و اسکیمای JSON **در زمان کامپایل از تایپ Rust تولید می‌شود** — اسکیما عملاً نمی‌تواند از کد فاصله بگیرد. یک `impl<T: Tool> ToolDyn for T` سراسری آن را به آبجکتی از جنس JSON-به-JSON برای رجیستری تبدیل می‌کند.

Claude Code یک اینترفیس `Tool` با `inputSchema` از جنس **Zod** به‌علاوهٔ فلگ‌های رفتاری (`isReadOnly()`، `isConcurrencySafe()`، `checkPermissions()`) تعریف می‌کند. آبجکت Zod هم آرگومان‌های مدل را اعتبارسنجی می‌کند و هم کل قرارداد در یک فایل است — ساده‌تر، پویا، و از ابتدا تا انتها خوانا.

جعبه‌ابزارهای داخلی به‌طرز چشمگیری مشابه‌اند — شاهدی بر اینکه این‌ها primitive‌های *درست‌اند*، نه دلبخواهی:

| کار | ابزار Grok | Claude Code |
|---|---|---|
| خواندن فایل | `read_file` | `Read` |
| ویرایش فایل | `search_replace` / `apply_patch` | `Edit` / `Write` |
| اجرای دستور | `run_terminal_cmd` | `Bash` |
| یافتن فایل/متن | `grep`, `list_dir` | `Grep`, `Glob` |
| وب | `web_search`, `web_fetch` | `WebSearch`, `WebFetch` |
| برنامه‌ریزی | `todo_write`, `enter_plan_mode` | `TodoWrite`، حالت plan |
| واگذاری | `task` (+ `wait_tasks`) | `Task` (ساب‌ایجنت‌ها) |
| پرسیدن از انسان | `ask_user_question` | `AskUserQuestion` |

### ویرایش فایل‌ها: بازنویسی کامل در برابر پچ فازی

اینجا جایی است که قراردادها بیشترین واگرایی را دارند. ابزار `Edit` در Claude Code جایگزینی دقیق `old_string → new_string` انجام می‌دهد با **الزام به تطبیق یکتا**؛ `Write` کل فایل را جایگزین می‌کند. از مدل انتظار می‌رود پیش از ویرایش، بخواند. ساده — و همان ایمنیِ «تطبیق یکتا یا شکست با صدای بلند» که در کلون خودتان هم می‌خواهید.

Grok سه موتور دارد: `search_replace` (کل فایل، دقیق، با حفظ CRLF)، یک موتور دیفِ پورت‌شده از Codex با **تطبیق‌گر خط فازیِ 4-سطحی** (تا خطوط کانتکست لازم نباشد بایت‌به‌بایت بخوانند)، و یک اکتور جداگانهٔ `xai-hunk-tracker` که **هر hunk تغییریافته را نسبت می‌دهد** به «نوشتهٔ ایجنت» یا «نوشتهٔ انسان» برای بازبینی.

برای ایجنت خودتان، از مدل Claude Code شروع کنید: **جایگزینی رشتهٔ یکتای دقیق، و شکست با صدای بلند اگر تطبیق یکتا نبود** — بالاترین نسبت ایمنی به تلاش را دارد. و یک ابزار باید هم در موفقیت *و هم* در شکست، **رشته‌ای که مدل بتواند بخواند** برگرداند: «No matches found» به مدل یاد می‌دهد دوباره بخواند؛ شکستِ خاموش از مسیر خارجش می‌کند.

## دادن شِل به ایجنت بی‌آنکه ماشین را دودستی تقدیم کنید

هر دو ایجنت به مدل اجازهٔ اجرای دستورات شل می‌دهند؛ و هر دو بعدش سخت تلاش می‌کنند این کار امن بماند. رویکردهایشان دو لایهٔ دفاعی را نشان می‌دهد که باید بفهمید.

**ترفند شلِ ماندگار.** یک ابزار شل ساده‌لوحانه هر دستور را در یک پروسهٔ تازه اجرا می‌کند، پس `cd` و `export` نمی‌چسبند. Grok از وضعیت شل اسنپ‌شات می‌گیرد: یک بار login shell اجرا می‌کند، بعد از یک marker محیط/cwd/aliasها را dump می‌کند، و برای هر دستور بعدی شل تازه‌ای می‌سازد، اسنپ‌شات قبلی را روی **fd 3** به آن پایپ می‌کند و وضعیت جدید را بیرون می‌کشد. دستورات از TTY کنترل‌کننده جدا می‌شوند تا پرامپت رمز عبور یک پروسهٔ فرزند نتواند TUI را خراب کند. Claude Code دستورات را از طریق یک شل مدیریت‌شده با cwd و محیط ماندگار اجرا می‌کند؛ خروجی گرفته و بریده می‌شود و تایم‌اوت اعمال می‌شود. دو باگ که گریبان هر ایجنت اولی را می‌گیرد: **خروجی بی‌سقف** و **نبود تایم‌اوت** — هر دو را زود درست کنید.

**سندباکس: چهار مکانیزم، یک هدف.** اینجا جایی است که دسترسی سطح-سیستمیِ Rust خودنمایی می‌کند. Grok ایزولاسیون سیستم‌عامل را **یک بار در استارتاپ**، به‌طور برگشت‌ناپذیر اعمال می‌کند، تا هم دسترسی فایلِ درون-پروسه و هم هر پروسهٔ فرزند را پوشش دهد:

| دغدغه | مکانیزم Grok | مکانیزم Claude Code |
|---|---|---|
| فایل‌سیستم (لینوکس) | Landlock | فیلتر seccomp-bpf |
| فایل‌سیستم (مک) | Seatbelt (`sandbox-exec`) | Seatbelt (`sandbox-exec`) |
| انکار زیرمسیرها (لینوکس) | re-exec با bubblewrap | پراکسی + policy |
| شبکهٔ فرزند | seccomp-BPF جلوی connect/bind را می‌گیرد | پراکسی شبکه با دامنه‌های مجاز |
| منبع policy | پروفایل‌های `.grok/sandbox.toml` | تنظیمات + `allowedDomains` |

Grok پروفایل‌های نام‌دار عرضه می‌کند — `workspace` (خواندن همه، نوشتن در ورک‌اسپیس، شبکه باز)، `read-only`، `strict`. یک قاعدهٔ حیاتی امنیتی: فایل `sandbox.toml` یک پروژه می‌تواند پروفایل **اضافه** کند اما **نمی‌تواند** پروفایلی را که سراسری تعریف شده بازتعریف کند؛ پس یک ریپوی مخرب نمی‌تواند policy سازمانی را از درون تهی کند. و **fail-closed** است: اگر نتواند یک deny را تضمین کند، به‌جای اجرای شُل، اجرا را رد می‌کند.

**تأیید کجا اتفاق می‌افتد.** این‌ها *دو لایهٔ مستقل‌اند* و خلط‌شان یک اشتباه کلاسیک است:

1. **تأیید (Approval)** — پیش از یک اقدام پرریسک از انسان بپرس (حالت‌های `Ask` / `Auto` / `AlwaysApprove` در Grok؛ `checkPermissions()` + `isReadOnly()` در Claude Code).
2. **سندباکس** — اقدام را *غیرممکن* کن، حتی اگر اشتباهاً تأیید شده باشد.

Grok نشان می‌دهد لایهٔ 2 در پروداکشن تا کجا می‌رود — و اینکه یک سندباکس خوب اجازه می‌دهد تأیید را *شُل‌تر* کنید، چون حالا کرنل است که قواعد را اجرا می‌کند. اول دروازهٔ تأیید را بسازید (ارزان است و جلوی بدترین اشتباه‌ها را می‌گیرد)، بعد آن را به یک سندباکس واقعی سخت کنید.

## جا دادن یک کار طولانی در حافظه‌ای کوتاه

پنجرهٔ کانتکست مدل متناهی است؛ کارهای واقعی کدنویسی نه. هر دو ایجنت این را در روح یکسان حل می‌کنند — و به‌طرز افشاگرانه‌ای، در جزئیات هم تقریباً یکسان.

**فشرده‌سازی (Compaction).** Grok در **85٪** پنجره فعال می‌شود (`DEFAULT_AUTO_COMPACT_THRESHOLD_PERCENT = 85`). استراتژی پیش‌فرضش جایگزینی کامل است: کل مکالمه را در یک خلاصهٔ ساخت‌یافتهٔ 9-بخشی خلاصه می‌کند (Primary Request، Key Concepts، Files & Code، Errors & Fixes، …)، سپس تاریخچه را به شکل `[system, user-prefix, AGENTS.md, last query, recent tail, summary]` بازمی‌سازد و خلاصهٔ قبلی را هم جلو می‌برد تا در فشرده‌سازی‌های مکرر چیزی گم نشود. Claude Code روی یک نردبان آستانه‌ای خودکار فشرده می‌کند به‌علاوهٔ یک **micro-compact** سبک که خروجی ابزارها را می‌تراشد؛ خلاصه‌ها همان جنس چیزها را حفظ می‌کنند و ترنسکریپت از یک درزِ «this session is being continued» ادامه می‌یابد. آستانهٔ 85٪ و الگوی خلاصه‌کن-بعد-بازسازی‌کن در هر دو تقریباً یکسان‌اند — وقتی دو تیم مستقل همگرا می‌شوند، با یک تکنیک **باربَر** طرفید. از همان ابتدا در ایجنت‌تان بسازیدش.

**شمارش توکن.** هر دو عمل‌گرا هستند. Grok از یک هیوریستیک خالص استفاده می‌کند — `bytes / 4` (یعنی `BYTES_PER_TOKEN = 4`)، و تصاویر یک عدد ثابت 765 توکن — عمداً تقریبی، و همین تنها منبع حقیقت برای دروازهٔ فشرده‌سازی است. Claude Code از شمارش مبتنی بر توکنایزر با هیوریستیک به‌عنوان پشتیبان استفاده می‌کند. یک تخمین‌گر `bytes/4` برای تصمیم دربارهٔ *زمان* فشرده‌سازی کاملاً کافی است.

**حافظه بین سشن‌ها.** Grok فایل‌های `AGENTS.md`، `Claude.md` و `.grok/rules/*.md` را از ورک‌اسپیس تا ریشهٔ گیت می‌خواند، به‌عنوان دستورالعمل‌های پروژه تزریق و در فشرده‌سازی حفظ می‌کند؛ یک حافظهٔ RAG آزمایشی هم جست‌وجوی هیبریدی BM25 + برداری با بازچینش MMR انجام می‌دهد. Claude Code فایل `CLAUDE.md` را برای دستورالعمل‌های پروژه/کاربر می‌خواند به‌علاوهٔ یک دایرکتوری حافظه که در آن هر واقعیت یک فایل با هدر توضیح است، و یک مدل کوچک چند مورد مرتبط با کوئری فعلی را برمی‌گزیند. هر دو: یک فایل دستورالعملِ کامیت‌شده + یک انبار هوشمندتر که ایجنت عندالمطالبه از آن می‌کِشد.

**سشن‌ها و ازسرگیری — تندترین تضاد.** Claude Code یک ترنسکریپت **JSONL فقط-افزودنی** به‌ازای هر سشن است — هر رویداد یک خط است، resume فایل را بازپخش می‌کند، بازیابی زنجیره را می‌پیماید. ساده‌ی ساده، و grep-پذیر. Grok وضعیت را روی ایندکس‌های **SQLite** قابل‌بازسازی (دیتابیس FTS5 + برداریِ حافظه؛ یک دیتابیس متادیتای worktree)، **چک‌پوینت‌های JSON بازگشت (rewind)** به‌ازای هر پرامپت، و ترنسکریپت‌های مارک‌داون پخش می‌کند؛ حتی یک کریت کوچک `xai-sqlite-journal` بسته به فایل‌سیستم بین WAL و TRUNCATE انتخاب می‌کند. JSONL = یک لاگ انسان‌خوان، بی‌دردسر برای بازرسی و بازپخش. تقسیم Grok = هر دغدغه در انباری که برازنده‌اش است (SQLite برای جست‌وجو، اسنپ‌شات‌های JSON برای rewind فوری). **با JSONL شروع کنید**؛ سراغ انبارهای تخصصی فقط وقتی بروید که یک قابلیت (rewind سریع، جست‌وجوی معنایی) طلبش کند.

## انسان ایجنت را چگونه می‌بیند

**UI ترمینال.** Grok یک اپ تمام‌صفحهٔ `ratatui` روی **صفحهٔ جایگزین (alternate screen)** است — بافر خودش، گرفتن ماوس، تم‌ها، اسکرول‌بک و جست‌وجو — به‌علاوهٔ یک حالت آزمایشی `Minimal` که بلوک‌های نهایی‌شده را در اسکرول‌بک *بومی* ترمینال چاپ می‌کند. Claude Code یک UI **این‌لاین** با Ink است: خروجی در اسکرول‌بک عادی جاری می‌شود، پس مکالمه‌تان بعد از خروج هم در ترمینال می‌ماند. Alt-screen یک قاب اپ ماندگار می‌دهد اما بافرش را هنگام خروج دور می‌ریزد؛ این‌لاین تاریخچه را در ترمینال شما باقی می‌گذارد و با pipeها ترکیب می‌شود، اما بازترسیم‌ها را باید خودتان مدیریت کنید. برای یک کلون، **این‌لاین انتخاب اول درست است** — چیز کمتری برای مدیریت دارد و با ترمینال ترکیب می‌شود.

**تعبیه در ادیتور: ACP.** Grok قابلیتی عرضه می‌کند که Claude Code جور دیگری حلش می‌کند — **Agent Client Protocol**، یعنی JSON-RPC جداشده با newline روی stdio که به یک ادیتور اجازه می‌دهد ایجنت را مثل جعبهٔ سیاه براند؛ همان پروتکل حتی MCP و افزونه‌های hook را هم تونل می‌کند. این نسخهٔ تمیز همان درزِ پیش‌گفته است: چون حلقه به یک *پروتکل* حرف می‌زند، هر فرانت‌اندی می‌تواند میزبانش شود.

**قطع کردن وسط نوبت.** هستهٔ interjection در Grok حالتی را مدیریت می‌کند که در حین کار ایجنت تایپ می‌کنید: پیام صف می‌شود و در نزدیک‌ترین نقطهٔ امن، به‌عنوان یک پیام کاربر مصنوعی قاب می‌گیرد («The user sent a message while you were working…») — **بدون هیچ** دستوری دربارهٔ نحوهٔ اولویت‌دهی؛ مدل خودش تصمیم می‌گیرد. نمونه‌ای کوچک و ملموس از طراحی برای انسانی که تا پایان نوبت صبر نمی‌کند.

## توسعه‌پذیر کردن ایجنت

ایجنت‌های پروداکشن باید بگذارند کاربران رفتار را بدون فورک‌کردن کد تغییر دهند. هر دو به همان سه مکانیزم می‌رسند — و Grok عمداً شکل‌های کانفیگ Claude Code را کپی می‌کند تا اکوسیستم سازگار بماند.

- **هوک‌ها.** Claude Code فرمت هوکِ `settings.json` را بنیان گذاشت: matcherها روی نام ابزارها، دستورات شلی که می‌توانند از طریق stdout/کد خروج یک ابزار را تأیید یا مسدود کنند، و شلیک در نقاط چرخهٔ عمر. Grok یک `settings.json` دقیقاً به شکل Claude Code می‌خواند (`PreToolUse`، `PostToolUse`، `UserPromptSubmit`، `SessionStart/End`…) و حتی نام‌های ایونت خارجی را روی نام‌های خودش نگاشت می‌کند — صادقانه‌ترین شکل تملق.
- **MCP.** هر دو **کلاینت MCP** هستند: به سرورهای خارجی Model Context Protocol (روی stdio یا HTTP/SSE) وصل می‌شوند و آن ابزارها را با فضای نام به مدل عرضه می‌کنند. این همان راهی است که هر کدام از این ایجنت‌ها بدون شیپ‌کردن کد جدید، ابزار دیتابیس یا مرورگر به دست می‌آورند.
- **ساب‌ایجنت‌ها.** هر دو ساب‌ایجنت‌ها را به‌صورت فایل‌های **مارک‌داون + frontmatter** تعریف می‌کنند که از طریق یک ابزار `task` در یک پنجرهٔ کانتکست تازه با allow-list ابزار مخصوص خودشان اجرا می‌شوند. Grok حتی برای سازگاری، دایرکتوری `.claude/agents/` متعلق به Claude Code را می‌خواند و ایزولاسیون **worktree** گیت را هم اضافه می‌کند تا ویرایش‌های فایلِ یک ساب‌ایجنت تا زمان merge، فیزیکی جدا بمانند.

الگوی زیر هر سه: یک **اینترفیس** پایدار — ایونت، اسکیمای ابزار، فایل ایجنت — که اشخاص ثالث بدون دست‌زدن به حلقهٔ اصلی‌تان هدفش می‌گیرند.

## چه چیزی را به ایجنت خودتان برگردانید

Rust در برابر TypeScript را کنار بگذارید و این دو ایجنت **همان یک ماشین‌اند**: حلقه‌ای که مدل را فراخوانی می‌کند، ابزارهایی که می‌خواهد را اجرا می‌کند، نتایج را برمی‌گرداند، وقتی پر شد فشرده می‌کند، و بخش‌های خطرناک را پشت تأیید — و در پروداکشن، یک سندباکس — دروازه‌بانی می‌کند.

تفاوت‌ها سلیقه‌اند. Rust در برابر TypeScript، تمام‌صفحه در برابر این‌لاین، SQLite در برابر JSONL — این‌ها انتخاب‌اند. اما حلقه، قرارداد ابزار، دروازهٔ تأیید، فشرده‌سازی در 85٪ — دو تیم مستقل به یک شکل به این‌ها رسیدند. این همان سیگنالی است که ارزش اعتماد دارد: **اول ماشین را بسازید؛ بقیه لایه‌های تاب‌آوری‌اند که دورش پیچیده می‌شوند.**
